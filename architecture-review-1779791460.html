도우미누오 / nuo-formatter

아키텍처 deepening 후보

R2(F30~F53) 종료 시점의 코드를 대상으로, 인터페이스가 구현만큼 복잡한 얕은(shallow) 자리와 중복된 seam(이음새) 들을 찾았다. 각 후보는 삭제 테스트로 판단했다 — 지우면 복잡도가 사라지면 통과, 여러 호출처로 흩어지면 그 자리는 깊어질 가치 있음.

9,720 LOC / 19 files ES5 · IIFE export · globalThis MV3 service worker + content scripts + MAIN bridges 2026-05-26 기준

읽는 법

Depth(깊이)

작은 인터페이스로 큰 동작. 좋음.

Shallow(얕음)

인터페이스가 구현만큼 복잡. 호출자가 다 알아야 함.

Seam(이음새)

인터페이스가 사는 자리. 1개 어댑터 = 가설, 2개 = 실재.

Strong 중복·결손이 명확하고 deepening 후 복잡도 집중 효과 큰 후보 Worth exploring 검토 가치 있음. 단 trade-off 확인 필요 Speculative 실측·논의 없이는 위험·이득 비교 불가

C1. 콘텐츠 패널 lifecycle 통합

Strong

Files

  • extension/calcFill.js (l.36 PANEL_HOST_ID · l.419 mountCalcSamplePanel · l.815~895 라우트·storage 와이어)
  • extension/teamBuilderFill.js (l.16 HOST_ID · l.227 mountTeamFloatBar · l.959~973 MO·라우트 와이어)
  • extension/speedOutspeedCalc.js (l.34 HOST_ID · l.745~750 attachShadow · l.1015 라우트 가드)
  • extension/calcFillShared.js (이미 nuoCsCommon — 헬퍼만 보유, lifecycle 없음)

Problem

세 floating 패널이 같은 9-step ceremony 를 각자 보유한다 — HOST_ID 정의 · document.body.appendChild · attachShadow({mode:'open'}) · buildShadow + style 주입 · chrome.storage.local.get([prefKey]) 기본값 분기 · chrome.storage.onChanged 구독 · onRouteChange 구독 · MO/setInterval 폴 · teardown 함수. nuoCsCommon 이 getRoute / onRouteChange / onLocalPrefChange / requestBridgeInject 4개 헬퍼만 export 하고, lifecycle 자체는 호출자 책임이라 매 패널마다 9-step 의 약 60%가 복붙. F31(calcFill 의 사망한 MO 제거)·F32(MO scope 좁히기)는 세 패널 중 한 곳만 손보면 다른 곳도 같이 손봐야 하는 시그널이었다.

Benefits

  • Locality — “smartnuo 콘텐츠 패널이 언제 뜨고 숨고 다시 마운트되는지”가 한 모듈로 모임. F31·F32 류 정정은 더 이상 3 군데 동기 갱신 아님.
  • Leverage — 4번째 패널 (예: 향후 docs 페이지의 인라인 어노) 추가 시 ceremony 0줄. 호출자는 render 와 gate 함수만 정의.
  • 테스트성 — lifecycle 핵심(가드·storage 디폴트·teardown 순서)이 헬퍼 단위로 vm 테스트 가능 (이미 scripts/smoke-formatter.js 패턴 존재).
  • 회귀 차단 — 옛 호스트 ID 가 남거나, storage 기본값이 팝업과 어긋나는 클래스 버그가 한 곳의 invariant 로.

Trade-offs

세 패널의 ceremony 가 100% 동일하진 않다 — calcFill 은 hover-dock + 좌측 puck, teamBuilderFill 은 MO + 슬롯 캐시 동기, speedOutspeedCalc 는 site 입력 wrap 추적 polling. 헬퍼 인터페이스가 옵션 7~8개로 부풀면 오히려 얕아진다. 안전한 단계 분리: (1) mount·attachShadow·HOST_ID·teardown 우선 통합 → (2) pref load+watch 정형화 → (3) route gate 정형화. MO/polling 까지는 자르지 않음 (각자 다른 트리거 의미).

C2. MAIN-world bridge 공통 reader 분리

Worth exploring

Files

  • extension/calcFillBridge.js (l.14~19 KEY_* · l.36~58 ensurePokeIxBuilt · l.609~621 message envelope)
  • extension/teamBuilderBridge.js (l.12~22 getNuxtState · l.42~67 ensureTbPokeIxBuilt · l.332 message envelope)

Problem

두 MAIN-world bridge 가 같은 일을 따로 한다:

graph LR subgraph calcFillBridge["calcFillBridge.js (V38)"] A1[getNuxtState inline] A2[ensurePokeIxBuilt byKr/byEn] A3[lookupByDex ability/equipment] A4[addEventListener message NUO_APPLY_CALC_V30] end subgraph teamBuilderBridge["teamBuilderBridge.js (V8)"] B1[getNuxtState inline] B2[ensureTbPokeIxBuilt byKr/byId] B3[waitForPokeListReady] B4[addEventListener message NUO_TEAM_GET_SLOTS] end A1 -.same.-> B1 A2 -.same shape, diff value space.-> B2 A4 -.same envelope, diff type strings.-> B4

getNuxtState() 는 두 곳 모두 동일 (window.__NUXT__.state || .payload.state). $spokemon_list 인덱스도 두 곳에서 같은 source-ref invalidation 패턴으로 따로 빌드 (F33 ↔ F35). 인덱싱 키 모음만 다름 (byKr+byEn vs. byKr+byId). postMessage envelope (source / type / requestId / ok / error) 도 동일 모양. 가드 버전 __NUO_CALC_BRIDGE_V38__ / __NUO_TEAM_BUILDER_BRIDGE_V8__ 도 의미상 같은 invariant 를 한 번씩 인코드.

Solution (sketch)

새 모듈 extension/nuoNuxtReader.js (MAIN-world, __NUO_NUXT_READER_V1__ 가드). SW chrome.scripting.executeScript 의 files 배열에서 bridge 보다 앞에 주입. export: 

window.nuoNuxtReader = {
  getState: function () { /* __NUXT__.state || .payload.state */ },
  pokeListIndex: function (state, keys) { /* lazy, source-ref invalidation */ },
  dexIndex: function (state, sectionKey) { /* lazy, byKr */ },
  installEnvelope: function (srcExt, srcReply, handlers) {
    /* addEventListener('message') + requestId + try/catch + postMessage */
  },
};

Trade-offs (왜 Strong 이 아닌가)

  • MAIN-world 모듈은 content_scripts 가 아니라 executeScript files. SW 측 inject 헬퍼를 한 군데 추가 (지금은 calcFillBridge·teamBuilderBridge 각자 하나만 주입). 주입 순서 보장 필요.
  • 가드 버전이 3개로 늘어남 (reader / calc / team). 셋 중 하나만 옛 버전이 살아 있으면 호환 매트릭스 복잡. 현재의 2개 가드도 사실상 잘 작동 중 — 회귀 없음.
  • 인덱스 인터페이스가 parameterize 깔끔하지 않음 — calcFillBridge 는 id/smogon_id/db_en/name 4 키 fallback, teamBuilderBridge 는 id + id.replace(/-/g,''). "키 배열을 파라미터로" 식의 통합이 readable 한지 의문.

현재 듀어레이션이 약 90줄 × 2 = 180줄. 통합 후 reader 100줄 + 양 bridge 의 호출부 60줄 = 160줄 정도 — diet 효과는 약함. 진짜 가치는 “Nuxt state 그래프가 바뀌면 한 군데 갱신” 자체. G16(state 키 fragility) 모니터링 부담을 줄이려는 의도면 의미 있음.

C3. Hold/Equipment/Ability boundary 정규화

Worth exploring

Files

  • extension/fmtCommon.js (l.30~69 collectHoldLabels — 10-키 whitelist)
  • extension/shareToRaw.js (koFromMaybeObj — URL 공유 경로 진입점)
  • extension/teamBuilderBridge.js (augmentSlotWithDex — 리뉴얼 후 슬롯 객체 진입점)
  • extension/simpleMovePower.js (findItemRule / findAbilityRule — 결정력 hot path)

Problem

slot.equipment / slot.ability 의 모양이 두 갈래로 들어온다 — (a) URL 공유 경로 = 문자열, (b) 리뉴얼 후 Nuxt slot = { kr, en?, slug?, ... } 객체. 계산 layer 가 양쪽을 다 알아야 하므로 collectHoldLabels 는 10개 alias 키 whitelist 로 모든 가능한 라벨 모양을 fallback. F50 의 실제 원인은 “리뉴얼 후 'kr' 필드가 진실인데 whitelist 에 'kr' 누락” → 화력증강도구 결정력 매치 끊김.

현재 collectHoldLabels 의 key whitelist

['kr', 'nameKr', 'name_kr', 'nameKO', 'labelKr', 'titleKr', 'name', 'label', 'title', 'slug', 'id']

→ 신규 진입점 추가 시 새 alias 무한 확장될 위험 (인터페이스가 구현만큼 복잡).

  • F50 류 회귀 차단 — 새 진입점 추가 시 alias 누락 → 결정력/내구력 무음 실패 클래스 제거.

C4. 결정력 7단 파이프라인 명시화

Speculative

Files

  • extension/simpleMovePower.js (l.200~422 oneMovePowerInternalDual 단일 220-줄 함수)
  • TEMPLATES.md §4.1 — 7단 순서 + Math.round 시점 자연어 명세

Problem

결정력 계산 = 베이스 → 태그 → 우격 → 노말스킨/-ate → 타입특성 → [조건부] → 도구 → STAB → 스탯 → 최종 7단. TEMPLATES.md 가 단계명·끼울 위치·Math.round 시점을 자연어로 정의했지만, 코드는 220줄 단일 함수 + 단계 경계가 주석으로만. F50·F52 디버깅 비용의 큰 부분이 “이 보정이 어느 단계에 들어가야 하나” 추적이었음.

Solution (sketch)

단계 경계를 내부 함수 7개로 추출 — 호출 순서 함수가 단계 명세를 코드로 인코드. (declarative array of steps 는 Math.round 위치 보존 부담으로 위험 — pass.) 

function oneMovePowerInternalDual(...) {
  var p = baseStep(mv);
  p = moveTagStep(p, ctx);
  p = griptechStep(p, ctx);
  p = ateStep(p, ctx);            // normal-skin / -ate
  p = typedAbilityStep(p, ctx);
  if (!skipConditionalAbility) p = conditionalAbilityStep(p, ctx);
  p = itemStep(p, ctx);
  p = stabStep(p, ctx);
  var dmg = statTimesPowerStep(p, ctx);
  return finalStep(dmg, ctx);
}

Trade-offs (왜 Speculative)

  • 줄수는 거의 그대로. depth 가치 = 가독성·디버깅. 측정 어려움.
  • 각 step 함수의 ctx 인터페이스가 부풀 위험 (rules / moveTags / moveKoMap / atkReal / spaReal / typeKoEn / Math.round positions …). 인터페이스가 단일 함수보다 더 얕아질 수도 있음.
  • R2 종결·스토어 제출 직전 시점. 이 작업 = 큰 회귀 surface. 다음 메커닉 추가 시점에 같이 자르는 게 합리적.
  • 대안: TEMPLATES.md §4.1 가 이미 잘 적혀 있음. 단계 라인 주석을 // === Step 4: -ate === 식 헤더 주석으로 강화하는 doc-only 변경이 ROI 더 좋을 수도.

짧은 cross-cutting 메모

  • Ko* / *Fallback JSON 4쌍 (move / item / ability + emerging type) — 이미 loadCalcPayloadDocs() 가 1차 통합 함. 추가 deepening 가치 낮음.
  • F38 sectionIxCache (WeakMap) — 같은 의미의 인덱스 빌더가 calc bridge / team bridge / fmtCommon 세 군데. C2 와 같은 정합 — 필요해지면 C2 우산 안에서.
  • $NUXT state 키 fragility (G16) — 키 문자열은 calcFillBridge.js·teamBuilderBridge.js 두 곳에만 묶여 있어, “여러 군데 흩어짐” 우려는 실측상 작음. 추가 추상화 불요.
  • scripts/smoke-*.js — Node vm 으로 fmtCommon + 계산 모듈 로드, modifiers.json·moveTags.json 직접 read. 이미 좋은 테스트 seam. 더 deepen 할 필요 없음, 사례를 늘리는 게 더 가치 큼.

Top recommendation

C1 — 콘텐츠 패널 lifecycle 통합

세 후보 중 가장 명확한 “두 어댑터 = 실재 seam” 사례. nuoCsCommon 이 이미 헬퍼만 노출하고 lifecycle 책임이 호출자에 흩어진 상태라, deepening 방향이 분명함 — 헬퍼 패키지 → 가벼운 lifecycle 헬퍼. 단계적 분리(mount/teardown → pref → route gate) 가 가능해 한 PR 의 회귀 surface 가 작음. 향후 4번째 패널(예: /docs 페이지 인라인 어노) 추가 시 즉시 leverage 가 살아남.

반면 C2 는 가치 있으나 가드 버전 sync·MAIN-world 주입 순서 추가 부담이 있고, C3 는 입증된 버그(F50) surface 가 있지만 shareToRaw 측 후방호환 검증이 추가 작업. C4 는 다음 메커닉 PR 때 함께 다루는 편이 ROI 가 큼.
